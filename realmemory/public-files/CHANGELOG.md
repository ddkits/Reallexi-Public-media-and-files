- Early infrastructure checkpoints now check delivered foundation files and strict JSON manifests without installing dependencies or running application scripts. A root build can delegate to packages that later chunks have not created yet; running it at this checkpoint held those chunks behind their own missing-file failure and could send repair toward removing valid build steps. Feature checkpoints keep their normal build and test checks, and final validation still requires the complete project and applicable UI proof.
- A model that thinks without ever answering is now stopped and reported as exactly that, on every provider lane. A planner request streamed reasoning for 187 seconds with not one character of answer, was killed only once the reasoning happened to pause long enough to trip an idle timer, and the rescue model then did the same thing past 185 seconds -- so a run could sit for minutes and end by blaming the network. The bound that prevents this already existed and was already tested, but it had been wired into two of the three stream readers and not into the one the default provider actually uses; the reader that carries production traffic armed no deadline at all, and reasoning chunks kept pulsing the idle timer forever. It is armed there now, bounded by what is left of the request budget so a late retry cannot restart the clock, and cleared only by real output -- a reasoning-only chunk carries an empty content field beside it, and counting that as the start of an answer is how the same bound was defeated once before. A model that deliberates for a long time and then writes a long reply is never interrupted, a tool call counts as an answer, and the failure now says the model spent N seconds reasoning without answering instead of reporting an anonymous transport timeout.
- MCP is now actually connected, rather than reported as ready. The extension shipped a working MCP server with eighteen tools and no client for it: nothing spawned it, nothing performed the handshake, and the shipped bundle contained no tool call of any kind. What existed was a check that the server file was present on disk, a session preflight that recorded the runtime as connected on both branches of its own test, and three settings that were declared and never read. So every capability a user would infer from "MCP runtime: ready" was unavailable, while the message said otherwise. There is a real stdio client now. It starts the bundled server and any server configured under realMemoryAgent.mcpServers, using the same entry shape other MCP hosts accept so a server definition can be copied across unchanged, performs the initialize handshake, discovers each server's tools and offers them to the model beside the built-in ones. Tool names are namespaced per server, which prevents two servers colliding and prevents an MCP tool being mistaken for a built-in one, and they are rewritten into the character set providers accept -- the bundled server names every tool with a dot, and a dotted function name is rejected outright, so exposing them unchanged would have made all eighteen unusable. A server that fails to start is reported with its reason instead of disappearing, and never takes the working servers down with it; a tool that reports its own failure returns that as output, because a model recovers from a failed tool and cannot recover from an exception that ends the run. Readiness now means a server was started, answered, and published tools. Servers are stopped when the extension shuts down, so none outlive the window.
- The bundled MCP server now speaks the transport the specification defines, so other MCP hosts can attach to it. It wrote length-prefixed frames, which no standard client expects, and its reader could only ever handle one message per chunk: it trimmed the entire buffer and required the whole thing to be a single JSON object, so a client sending the handshake and its acknowledgement together produced one unparseable string and the connection could never complete. Messages are newline-delimited now in both directions, framing is decided per message rather than per chunk, and the older length-prefixed input is still accepted so nothing that already worked stops working.
- The NVIDIA model shipped as the default had been retired by the provider, so a fresh install failed on its first request. openai/gpt-oss-120b reached end of life on 2026-09-03 and answers every request with a permanent 410; it was the default for the single, planner and coder model settings, the first entry of the built-in rescue ladder, and one of the models offered in the picker before the live catalog loads. The selected model and its first rescue were therefore both dead, and a run could spend its whole retry ladder without reaching a working model. The default is now a current model, the rescue ladder tracks that default instead of naming a model a second time where it can go stale, and the retired id is kept only as a migration alias -- an install that saved it is moved onto the working default automatically rather than being left permanently broken. The models the codebase already recorded as retired are no longer offered in the picker, and the browser extension's suggestion text no longer recommends the dead model by name.
- A repair that repeats is now stopped and handed over instead of being tried again forever. Cards were arriving marked "seen 69x" and "seen 71x": the same subtask diagnosed and repaired dozens of times, every round ending in the identical failure. An eight-attempt budget already existed for roadmap chunks, but the two counters above it were bounded by nothing. The repeated-failure count was measured on every diagnosis and spent only on making the prompt more emphatic, and the validation loop's only exit counted consecutive identical failures that changed no source -- a counter that resets to zero the moment any repair writes anything, so a loop whose repairs kept editing something while the failure stayed the same never ended. Both now stop at the same eight. The subtask that cannot be fixed moves to Blocked on the board with its failure fingerprint and count attached, a repair item is queued for a later lane, and the run carries on with the rest of the work rather than spending itself on one item. Blocked is a pause, not a verdict: the item keeps its evidence and is reopened when new evidence arrives.
- When a repair cannot be made safely, the model is now told exactly what to do instead of being handed a sentence. One card recorded its entire technical detail as the word "apply_repair", sixty-nine times. The deterministic layer had read the config, walked the project and established precisely which directories hold its sources -- and then discarded all of it and emitted one line of prose, so each round had to rediscover the same facts and guessed differently. A declining repair now states a requirement: what failed, what was read off the disk, the exact edit permitted, and the test that decides whether it worked. It is structured rather than prose, and bounded to the files it names, so a config repair cannot become a project rewrite. Nothing in it is written per error type; every field is filled from evidence already in hand, so a failure nobody has seen yet states its requirement the same way.
- A TypeScript project whose sources have moved is repaired as one change rather than two. A config saying its sources are in ./src when they are in ./apps/api/src compiles nothing and reports "No inputs were found"; the search meant to find the real sources gave up three directories down and collapsed what it found to the first path segment, which for that layout either found nothing or proposed a glob that would have pulled a sibling application into the wrong compile. It now walks bounded by work rather than by an assumed nesting depth and names the directory that actually holds the sources -- no directory name is privileged, so a layout nobody has shipped yet resolves the same way. The first version of this fix repointed the include and left rootDir behind, trading one compiler error for another; the check that approves a config repair counted input files and would happily approve a config that names its inputs and then forbids them. A repair is now approved only when the config that comes out both names inputs and contains every one of them, and every path that rewrites an include reconciles rootDir with it.
- Missing type declarations and unresolved names are told apart by reading what is installed. A build failing with both "could not find a declaration file for module 'express'" and "cannot find name 'Express'" used to repair only the first: the compiler prints the exact package to install for one and prints nothing at all for the other, so each round installed what it was told and the second error survived untouched. Rather than keep a list of which global comes from which package -- a list that is wrong the first time a project uses something not on it -- the installed declaration files are read. A name some installed declaration provides is a configuration problem and is repaired; a name nothing provides is a source problem that no install can reach, and it is reported as such with the packages that were inspected. Where a project narrows compilerOptions.types and thereby keeps an installed declaration from loading, that list is widened and never trimmed.
- A package manager missing from PATH no longer costs a run. A workspace whose build script calls pnpm on a machine without it produced fourteen identical rounds: the deterministic layer correctly answered that no dependency can supply a package manager, the install it then reached for was global, and the run guard exists to refuse exactly that -- so the model proposed the one command the guard blocks and every round ended where it started. corepack ships with Node, honours the version the workspace pinned, installs nothing and needs no consent, so the scripts are routed through it. Only the executable position of a command is rewritten, a manager that answers is left alone, and running the repair twice changes nothing the second time.
- Bug cards now name the step that failed instead of listing every step that was planned. A card's "failing command" field held all seventeen commands of a validation plan; sixteen of them never ran, because the runner stops at the first failure. Reconstructing which one failed from the output could not be done reliably -- npm, pnpm and yarn each print their run header differently and a step that runs a plain script prints none -- so the runner now says which step it is on before it starts, and the last thing it said is the step that failed. Steps that did not run are reported as not having run. Two further loops are closed with the same care: a module that exports a function by name is no longer reported as failing to export it, and a file listed in a script with commas between the names is recognised as a punctuation defect rather than a missing module, both confirmed against the files on disk before anything is changed.
- A roadmap chunk now closes on its own delivery instead of on a path another chunk happened to write. Observed on a board that did not move for a week: nine chunks Closed, while "Chunk 4: Frontend/product slice (packages)" and "Chunk 11: Docs and handoff (apps)" sat at Planned 0%, the planner repeated "Every deterministic roadmap target already has case-insensitive workspace evidence", and the Validator reported it could not start until Writer closed all bounded chunk tasks. Nothing was wrong with the work. Chunk 3 had written packages/rules/package.json and packages/rules/src/index.ts -- paths chunk 4 also listed as targets -- and closure was computed from one global set of written paths, so chunk 4 was marked done before anything opened it: never ready, therefore never dispatched, therefore its task row never closed, therefore the gate never opened. A permanent deadlock produced entirely by two chunks sharing a file name, which is normal in a roadmap that splits manifests from the product slice of the same component. Dispatch is now recorded on the chunk when a lane claims it, closure requires both the targets and that record, and the persisted chunk status uses the same rule as the scheduler so the board and the scheduler can no longer disagree about what is finished. Work a previous run really did close is recognised from the same task rows the board displays, so a resumed mission does not redo it, and the incremental path without an authoritative specification keeps its cheaper behaviour where existing files close a chunk.
- UI screenshot validation is no longer pointed at packages that have no page. The target used to be the first changed package that declared a build script, which on one monorepo was the HTTP API: the validator found no preview script there, fell back to a static snapshot with nothing rendered in it, and the same diagnosis came back three times telling the agent to add a preview script to a package that has nothing to preview -- while the Vite app in the same workspace, built and tested by the same run, was never looked at. A directory is a UI target now when something in it renders in a browser: a page on disk, a dependency whose job is producing or serving pages, or a script that runs one of those. Those are facts about the package rather than a list of directory names, so a workspace that calls its UI storefront is found and one that calls its API web-api is not, and what a script would actually run is read rather than what its text contains -- vite-node src/index.ts is a Node loader, not a web server. The chosen package is logged with the reason it was chosen, changed packages that were passed over are named, and the validator itself now says when a directory has nothing a preview script could serve instead of only reporting the missing script.
- A manifest script that has to be quoted is written as a file instead. A test script holding an inline node -e program has to survive JSON string escaping and shell quoting at once, and losing either one leaves a package.json that npm cannot read, so install, build, test and lint all die before they start -- reported thirteen times on one workspace, on a program that was itself checking that package.json is valid JSON. Refusing the write kept a good manifest from being replaced but never ended the round, because the next attempt wrote the same program with the same quoting. The program now goes where quoting costs nothing: a file beside the manifest, with the script pointing at it. A manifest that already arrived broken is recovered one line deep and only when the value that broke it turns out to be a script -- a version range has to be exactly what the writer meant, so a manifest broken there stays refused -- and a recovered program that no longer parses as JavaScript is replaced by a check that the manifest parses and the files it declares exist, rather than copied out to fail in a new place.
- A failure now carries the location it was printed with. A card was filed sixteen times whose entire description was "SyntaxError: Invalid or unexpected token" -- no file, no line, no token -- because every reader that turns captured output into text keeps the lines that look like failures, and a location carries no error word in it. Node had said exactly where four lines earlier, and all four lines were dropped as transcript. A location is part of an error, not context around it, and every toolchain prints it the same way: above the message, as a path with a line number, usually followed by the offending source line and a caret. So a kept failure now keeps the frame directly above it, in the order it was printed, and the diagnosis reads the file, the line, the column and the offending source out of that frame rather than paraphrasing the message. A location proved from the tool's own output is preferred over a model's account of the same output, because the model is summarising exactly what was missing.
- An inline program in a package script is moved into a file, which is the only way it runs on Windows. node -e 'console.log(1)' cannot work under cmd.exe, which does not treat a single quote as a quote and hands it to Node as the first character of the program; the result is "SyntaxError: Invalid or unexpected token" on every Windows machine whatever the program says, and it was reproduced exactly against the preview script of the workspace that filed the sixteen cards -- the same script the UI validation step starts before taking a screenshot. Because the program is an argument rather than a file, Node reports it as [eval]:1, which is now read as the location it is: the diagnosis names the npm script that passed the program, quotes what Node actually received, and says plainly that the quoting is the defect. The repair is deterministic and needs no model: the program moves into a file beside its manifest and the script becomes node <file>.cjs, with the shell taken out of the question entirely. It applies to a program anywhere in a script, so a build script that runs two package-manager steps before an inline program keeps both and loses only the quoting, and the program's own backslash-escaped quotes are put back when that is what stood between it and parsing. A generated file name never claims one the directory already has.
- The Chromium UI validation step now reports what a dev server said when it failed to start, instead of only that it exited. "exited early (code 1)" with the child's output discarded is the same undiagnosable shape as a syntax error with no location, and it hid exactly that failure: the preview script died on its own quoting and the run recorded a code, not a cause.
- A repair that makes the failure worse is now undone automatically, in any language. Every deterministic repair knows one specific thing -- a compiler config, a lockfile, a script name -- and can only recognise the failure it was written for, so when a repair damages a project nothing catches it: the damage is a new failure of a shape no repair claims. That happened three times in a single evening in this codebase, each time turning a compile error into a project that built nothing, and each time the loop continued as though progress had been made. The rule that fixes this asks nothing about languages or file formats. A repair writes files; validation reruns; if the new failure mentions a file that repair just wrote and the previous failure did not, the repair caused it, the write is restored to the exact bytes that were there before (or deleted, if the repair created it), and the loop returns to the original failure rather than the damage. It matches on the paths the repair itself recorded rather than on any list of known source extensions, so a Cargo.toml, a go.mod, a requirements.txt and a Makefile are covered the same as a tsconfig. A repair that simply did not work is untouched by this: failing the same way twice is not a regression, and reverting that would mean nothing could ever land.
- TS18003 -- a TypeScript project with no input files at all -- is now repaired from the message itself, in every shape it takes. The error states the config, its include paths and its exclude paths, and a project ends up with no inputs in exactly one of three ways: an exclude resolves to the project's own directory so nothing can match, an exclude covers every include so the list is cancelled out, or every include points at another project so the config never named its own sources. The first two are fixed by dropping the offending exclude; the third needs the project's real source directories, because dropping anything would leave it empty. That last case is not hypothetical -- an earlier repair in this series added an exclude that cancelled the only include a config had, and neither of the narrower repairs recognised the result, so the same failure came back three times. Whatever the shape, the source directories are read from disk and a config is written only when the include list that comes out of it is non-empty; when the project genuinely has no sources to point at, the blocker is recorded instead of writing a config that cannot work.
- A project that compiles another project's sources now has its include list fixed rather than its exclude list extended. The 1.5.119 repair worked as far as it went -- it excluded the frontend from a backend tsconfig and all 78 JSX errors disappeared -- but it then left TS7016 and TS2307 coming from ../packages/rules and ../packages/schema, separate projects with their own builds whose files carry no JSX and so never matched a JSX error code. Every compiler error against a file outside the project is the same ownership problem, whatever its code, and whether a directory really belongs to someone else is decided from the workspace: it counts as foreign only when it has a manifest or a tsconfig of its own, so a plain shared folder stays compiled by whoever includes it. Excluding was also the wrong shape of repair for the config that prompted it, whose include listed only foreign sources and none of its own -- excluding them all would have left it with no inputs and turned one failure into TS18003, the same trap from the other direction. Foreign entries are dropped from include, the project's real source directories take their place when nothing of its own remains, and a config that would end up with no inputs is never written: the blocker is reported instead.
- The tsconfig repair released in 1.5.118 could edit the wrong project, and did: it chose its target from the failing project root, which resolved to the frontend, and wrote exclude ../frontend into frontend/tsconfig.json -- where that path is the project's own directory, so the frontend compiled nothing and failed with TS18003 while the backend config that actually listed ../frontend/src in its include was never touched. A repair that can erase a working project is worse than the failure it was written for. Ownership is now decided from the files themselves: the config to fix is the one whose own include reaches outside its directory and names a directory the compiler blamed, an exclusion that resolves to the project it would be written into is refused outright, and a project already carrying such an entry is restored automatically because TS18003 names the config, its include paths and its exclude paths. The decision is a pure function tested against both real configs from the workspace where this happened, because the first version shipped with a green suite: the tests covered which directories to exclude and how to write them, while the choice of which file to edit lived inside filesystem code where the only assertion was that it was wired in. Separately, the validation runner now decides installs at execution time rather than trusting a flag recorded when the command was built, so a command replayed from an older version still installs; a workspace whose frontend declared vite the whole time had been failing with vite not recognized for exactly that reason.
- Three bugs reported from the board are fixed and now have permanent regression tests, so every release has to answer for them. A backend tsconfig that reaches outside its own directory pulled the frontend and the browser extension into the backend's compilation, where JSX has no --jsx flag and the DOM lib is absent; that was reported eleven times with a correct diagnosis every round, and the directories the compiler names are now excluded deterministically instead of waiting for a model to rewrite the config. A validation step built without the ensure-dependencies flag ran against whatever tree happened to be on disk, so a root build died three times with vite not found while no step would ever install it; ensuring is the default now and must be switched off explicitly, and it stays cheap because the runner still installs only when the tree is missing or older than its manifest. And a bug card was filed carrying twenty base64 runner steps and no failure at all -- no root cause, no failing line, no output -- so cards now decode nested runner steps into the commands a person would type, and a card with no captured output says so plainly instead of leaving a reader with a command and nothing else.
- A pnpm catalog: dependency reference with no catalog to read from is now declared automatically, because that failure stops an install and therefore stops everything. Measured on a live workspace: 20 generated manifests used the catalog protocol in 25 places while pnpm-workspace.yaml declared no catalog at all, so every install ended at ERR_PNPM_CATALOG_ENTRY_NOT_FOUND_FOR_SPEC before one file was compiled -- eight validation attempts, the identical error each time, and 39 of 50 roadmap chunks left waiting behind an infrastructure gate that could not open while install was broken. The versions are recoverable from the workspace itself: a sibling manifest that pins the same dependency, or the copy already present under node_modules. Those are written into pnpm-workspace.yaml in a single pass rather than one install failure at a time, merged into an existing catalog block when there is one, never overwriting a version the workspace already declares, and quoting scoped names so the file still parses. A dependency whose version cannot be proven from the workspace is named in the error instead of being given an invented one, so the model repair that follows has a single bounded question rather than twenty-five.
- JSON is now the transport for every model call, not a property of some prompts. Contract turns always stated their own schema, but a free-form turn stated nothing, so prose remained a reachable output -- one observed Writer turn spent 220,153 characters narrating its own instructions and emitted no answer at all, and the bounded repair that followed produced 220,172 characters of the same. Every non-tool request now carries the JSON-object decoding constraint (response_format json_object on OpenAI-compatible endpoints including NVIDIA NIM, format: json on Ollama), a request that does not define a schema of its own is told to answer as {"text": "..."}, and that envelope is unwrapped once at the single point every caller reads provider text, so code expecting prose still receives prose and a contract answer is still delivered exactly as the model wrote it. Only a single-key envelope is unwrapped, so no multi-key contract can be mistaken for one. Tool turns are the deliberate exception and need no constraint: a tool call already travels as JSON arguments against a JSON schema. Images continue to travel base64-encoded inside the same JSON bodies, and an endpoint that refuses the constraint is learned once, retried immediately without it, and remembered across sessions.
- A request that demands JSON now constrains the decoder, so a contract turn cannot come back as prose. Asking a model for JSON in words is a request; asking the provider for it is a constraint, and only one of those is enforceable. Observed live: a Writer turn returned 220,153 characters narrating its own instructions -- "We are in the Writer worker. We are to return a JSON with either..." -- without one character of the contract, the bounded schema repair asked again and received 220,172 characters of the same narration, and only a third and much smaller call produced a usable patch. - A repair no longer proposes edits to a file it has never read, which was the single largest source of wasted repair rounds.
